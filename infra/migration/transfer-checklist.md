# ПАНДА: протокол безопасного переноса данных

**Статус:** проект процедуры. Ни одна команда переноса или отключения рабочих сервисов не выполнялась.

## Что переносим

- База PostgreSQL: таблицы, записи, права доступа, функции, триггеры и историю; поддержка PG17.
- Сотрудники и авторизация: записи `auth.users`, проверка ролей и нового входа, настройки отправки почты.
- Три приватных файловых раздела: `avatars`, `ved-commercial-offers`, `ved-product-photos`.
- Секреты маркетплейсов: повторное шифрование в новой базе через админку ПАНДЫ, без публикации значений в GitHub и логах.
- Задания: 20 Vercel cron и 3 сетевых SQL cron перенесены в собственный, по умолчанию выключенный планировщик; локальный cron заметок остаётся SQL-заданием.

## Этапы: без изменения работающей ПАНДЫ

1. Запустить пустой официальный Supabase и веб-контейнер в **отдельной тестовой среде**, без публичного доступа к БД.
2. Сохранить резервные копии ролей, схемы и данных исходной платформы по **официальной** инструкции Supabase CLI:
   ```bash
   # Только в защищённой машине, с правильно настроенным CLI.
   # Внешний пароль не передавать как аргумент в общем терминале или чатах.
   supabase db dump --db-url "$SOURCE_DATABASE_URL" --role-only -f roles.sql
   supabase db dump --db-url "$SOURCE_DATABASE_URL" -f schema.sql
   supabase db dump --db-url "$SOURCE_DATABASE_URL" --use-copy --data-only -f data.sql
   ```
   **Важное ограничение:** официальное копирование может требовать настройки расширений и совместимости версий Auth/Storage. Нельзя восстанавливать дамп автоматически в рабочую базу.
3. На **восстановленном и изолированном** экземпляре проверить SQL-планировщик и исполнить `infra/supabase/disable-obsolete-cloud-cron.sql`: три старых задания, обращающихся к Vercel, должны быть отключены **до** разрешения исходящих запросов.
4. Перенос файлов делать **через объектный протокол S3 с rclone**, а не копировать выгруженные файлы прямо в каталог `volumes/storage`. Последнее официально не поддерживается и может дать некорректный файловый формат. В целевой базе должны быть созданы три приватных bucket. Настроить два закрытых подключения (`platform` и `self-hosted`) через официальный пример; хранить их логины и пароли только локально. На тесте:
   ```bash
   rclone copy platform:avatars self-hosted:avatars --progress
   rclone copy platform:ved-commercial-offers self-hosted:ved-commercial-offers --progress
   rclone copy platform:ved-product-photos self-hosted:ved-product-photos --progress
   rclone size platform:avatars
   rclone size self-hosted:avatars
   ```
   Проверить количество объектов, размеры, а также реальное открытие нескольких файлов через приватные подписанные ссылки.
5. Сопоставить результаты SQL `read-only-inventory.sql` из источника и новой базы: кол-во таблиц, сотрудников, файлов, безопасность секретных функций. Сверить критичные финансовые суммы и остатки на выбранных датах. Размер БД может отличаться после восстановления из-за индексов и очистки.
6. Ключи Ozon, WB, Яндекс Маркета и MPStats перенести в **новый** Vault безопасным повторным вводом через раздел администрирования, проверить подключение. Записи старого Vault без нужного корневого ключа не считаются перенесёнными.
7. Проверить закуп, склады, историю расчётов, ВЭД, фото, юнит-экономику, рекламные затраты, роли, 1С, выгрузки. Не вызывать реальную синхронизацию в тестовом контуре без отдельной блокировки или тестовых данных.
8. Только затем назначить окно переключения, остановить старые задания, прекратить запись в облачную базу, выполнить окончательную синхронизацию, перепроверить суммы, файловые ссылки и авторизацию. Старую систему сохранить для отката на согласованный срок.

## Предупреждения

- Три действующих SQL cron сейчас вызывают старый Vercel. Их команды могут содержать чувствительные значения. **Никогда не выводить полное поле `cron.job.command` в логи.**
- Официальный self-hosted Supabase даёт PostgreSQL, Auth и Storage, но не обеспечивает автоматически внешние резервные копии и обслуживание сервера. Разработать расписание зашифрованных резервных копий и тесты восстановления до запуска.
- Перенос `storage.objects` в дампе и повторная загрузка S3 могут потребовать согласования метаданных. Проверять на тестовой базе, не полагаться только на совпадение количества файлов.
- Важные параметры Supabase (JWT, OAuth, SMTP, разрешённые адреса входа) на новом сервере требуют самостоятельной настройки; после переезда всем сотрудникам может потребоваться повторный вход.
- Не переносить зашифрованные секреты старого Vault как работоспособные без доказательства наличия старого ключа расшифровки.
