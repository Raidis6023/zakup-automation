# ПАНДА: этап 1, аудит перед Docker-миграцией

**Дата фиксации:** 2026-11-19
**Репозиторий:** `Raidis6023/zakup-automation`
**Рабочая ветка:** `migration/docker` (создана от `main`)
**Статус:** первичный статический аудит + безопасные SQL-запросы на чтение. Проверка запуска Docker и полноценная инвентаризация не проводились. Продакшен не меняли.

## 1. Исходная система

- Next.js 16.2.4, React 19.2.4, Node.js runtime; `next.config.ts` пока не включает `output: "standalone"`.
- `package.json` содержит длинную цепочку регрессионных тестов, подготовку изображений `scripts/prepare-login-panda.mjs`, тесты юнит-экономики и `next build`. При контейнеризации нельзя пропустить эти стадии.
- Прямые зависимости: `@supabase/ssr`, `@supabase/supabase-js`, `sharp`, `exceljs`, локальный пакет `xlsx` из `vendor/xlsx-0.20.3.tgz`.
- `package-lock.json` присутствует. `Dockerfile`, `.dockerignore`, `docker-compose.yml`, `compose.yaml` на момент аудита не обнаружены.
- `.gitignore` игнорирует `.env*`, `.next`, `node_modules`; при создании примера переменных потребуется исключение для `.env.example`.

## 2. Зависимости от Vercel, выявленные в коде

- **Критично:** `app/api/wb/daily-sync/route.ts` задаёт `const origin = "https://zakup-automation.vercel.app"` и вызывает внутренний синхронизатор через этот адрес. Без исправления новая установка продолжит обращаться к старому хостингу.
- **Критично:** `app/api/yandex/daily-sync/route.ts` использует `VERCEL_PROJECT_PRODUCTION_URL` / `NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL`, затем fallback `https://zakup-automation.vercel.app`. Нужно перейти к проверяемой настройке внутреннего адреса или прямому вызову серверной функции.
- `vercel.json` содержит **20 заданий** по расписанию. Следует перенести их в собственный планировщик и исключить двойные вызовы во время переключения.
- Документ `docs/1c-export-v1.md` описывает заголовок обхода Vercel Protection; при переносе обновить документацию и внешний защищённый маршрут.
- Комментарии и сообщения об ошибках Vercel в маршрутах нельзя путать с реальными обязательными зависимостями; ревизовать отдельно.

## 3. Supabase и PostgreSQL: текущие наблюдения

Проверка на чтение подключённого проекта `zlkluzcjppefelgwihyz`:

- PostgreSQL **17.11**; объём текущей базы около **1300 MB** (значение `pg_database_size`, не размер резервной копии).
- **123** таблицы в `public`, у всех включён RLS (это ещё не подтверждение корректности всех правил доступа); **4** политики `public`.
- В `auth.users` **3** учётные записи.
- Хранилища файлов, все приватные:
  - `avatars`: 2 объекта;
  - `ved-commercial-offers`: 4 объекта;
  - `ved-product-photos`: 38 объектов.
  - Всего **44 объекта**. Сохранить именно содержимое файлов, не только таблицу `storage.objects`.
- Активные задания `pg_cron` (плюс к Vercel):
  - `app-personal-notes-v1` — каждую минуту;
  - `ozon_finance_ads_backfill_10min` — на самом деле **каждые 5 минут** согласно текущему расписанию;
  - `yandex_finance_recovery_10min` — каждые 10 минут;
  - `yandex_promotion_recovery_10min` — каждые 10 минут, с началом в 5-ю минуту.
- Используются расширения `pg_cron`, `pg_net`, `pgcrypto`, `uuid-ossp`. Нужна проверка совместимости выбранной самостоятельной установки Supabase, её PostgreSQL, расширений, схем `auth` и `storage`.
- Размер базы и число таблиц не равны полному размеру данных: отдельно проверить Storage, конфигурацию служб, очередь задач, журналы и секреты.
- **Не следует** переносить файловые каталоги Postgres напрямую между несовместимыми версиями. Для миграции выбрать совместимый способ резервного копирования/восстановления и провести пробное восстановление.

## 4. Секреты и внешние интеграции

- `lib/integrations/secrets.ts`: секреты Ozon, WB, Яндекс Маркета и MPStats читаются через `workspace_get_integration_secrets`, с fallback на переменные окружения.
- Коды некоторых маршрутов читают ключи непосредственно из окружения, например `app/api/china/wb-operational-sales-sync/route.ts` требует `WB_READ_TOKEN`. Требуется единая матрица «переменная / источник / использующие маршруты».
- `lib/unit-economics/source.ts`: доступ к Google Sheets через `GOOGLE_SHEETS_CLIENT_EMAIL` и `GOOGLE_SHEETS_PRIVATE_KEY`; при недоступности используются локальные снимки. Этот внешний сервис сохраняем или отдельно согласовываем замену.
- `lib/supabase/client.ts`, `admin.ts`, `server.ts`, `proxy.ts`: зависят от `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`. Не размещать секретные значения в Git, образе или публичных `NEXT_PUBLIC_` переменных.
- Отдельно проверить настройки URL для регистрации, подтверждений, cookie, обратного прокси и внешних интеграций.
- Для `NEXT_PUBLIC_` учесть встроенные в клиентскую сборку значения при `next build`: смена адреса может потребовать пересборки образа.
- `app/api/v1/1c/export/route.ts`: экспорт 1С должен оставаться защищённым и доступным по новому адресу.
- Инвентаризация переменных окружения по всем файлам пока **не завершена**. Секретные значения не считывать и не коммитить.

## 5. План следующей стадии (Docker-образ)

1. Зафиксировать точную поддерживаемую версию Node.js и базовый образ; учесть `sharp` и `vendor/xlsx-0.20.3.tgz`.
2. Добавить `.dockerignore`, Dockerfile (многоэтапная сборка), `next.config.ts` standalone, `compose.yaml` для локальной проверки веб-приложения и `.env.example` без секретов; поправить правило `.gitignore` для примера.
3. Устранить жёстко прописанные адреса Vercel и определить безопасный путь внутренних вызовов; проверить, что внутренние маршруты защищены.
4. Обеспечить корректное использование переменных `NEXT_PUBLIC_` на стадии сборки, серверных секретов только при запуске.
5. Проверить `docker compose config`, `docker build` и тест запуска в изолированном окружении. Не направлять тестовую сборку на рабочую БД для записи.
6. Подготовить собственный планировщик с защитой от дублей, таблицей расписаний и контролем успешности; фактический запуск только после переноса и проверки данных.
7. Отдельным этапом развернуть проверенный совместимый стек Supabase/PostgreSQL, протестировать восстановление и авторизацию.
8. Согласовать с администратором серверные характеристики, резервное копирование, HTTPS и внешний доступ.

## 6. Нерешённые вопросы для следующей проверки

- Полный список переменных окружения и фактических их потребителей.

- Запуск сборки и всех регрессионных тестов на целевой архитектуре.

**Правило этапа:** не менять production `main`, рабочую базу, cron и секреты до отдельной проверки.
