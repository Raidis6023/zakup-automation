# ПАНДА: проект решений по секретам, фотографиям и адресам

**Дата:** 2026-11-19
**Ветка:** `migration/docker`
**Статус:** предложение для согласования и реализации после проверки совместимости. Никакие настройки production не менялись.

## 1. Хранилище секретов интеграций

**Требование:** оставить существующее управление токенами из интерфейса администратора ПАНДЫ. Замена токена через UI должна сразу отражаться в работе сервиса без пересборки Docker.

Текущая реализация:
- `app/api/admin/integrations/route.ts` проверяет авторизованного пользователя и административные права; `POST` вызывает `workspace_upsert_integration_secrets` и регистрирует метаданные события в `app_audit_events`, затем инвалидирует кэш.
- `lib/integrations/secrets.ts` использует `workspace_get_integration_secrets`; кэш действует до 5 секунд.
- Проверкой только на чтение подтверждено наличие обеих функций в действующей БД: `security_definer=true`, прямой EXECUTE только у `service_role`, не у `anon` и `authenticated`. Проверка SQL-текста на наличие поддержки WB/ЯМ/MPStats положительна.
- Есть fallback на переменные окружения; часть маршрутов читает окружение напрямую (например, WB China operational), поэтому до миграции необходимо унифицировать источники.

**Рекомендуемая архитектура:** самостоятельный Supabase Vault при подтверждённой совместимости (или независимое зашифрованное приватное хранилище в PostgreSQL, если Vault недоступен). Мастер-ключ шифрования хранить отдельно от базы и от GitHub, с использованием защищённых файлов/secret mount в инфраструктуре. Для сервисных паролей и ключей инфраструктуры использовать Docker Compose Secrets или эквивалентное защищённое хранение на сервере. Не класть динамические ключи маркетплейсов в Dockerfile, GitHub, .env или клиентскую сборку.

**Перед запуском:** проверить рабочие функции Vault в целевом стеке, шифрование, роль исполняющего сервисного пользователя, права UI и аудит. Старые зашифрованные данные Vault требуют корректного корневого ключа; предпочтительный безопасный вариант — переустановка секретов через существующий UI в целевое хранилище, а не перенос непрозрачного шифротекста без ключей.

Проверка подключения при обновлении ключа, версия/дата изменения, реальный статус и маскированное представление — возможные доработки; не утверждать, что они уже все реализованы.

## 2. Фотографии и файлы

Текущий Storage, размеры **по metadata** (не фактический физический размер томов):
- `avatars` — 2 объекта, около 0.01 МБ;
- `ved-commercial-offers` — 4 объекта, около 17.36 МБ;
- `ved-product-photos` — 38 объектов, около 0.53 МБ.

**Рекомендуемый первый вариант:** Supabase Storage с локальным файловым backend и постоянным монтированным серверным каталогом (путь уточнить с сисадмином; например, `/srv/panda/storage`). Сохранить существующие bucket/paths, приватный доступ и подписанные ссылки, не переписывать клиент.

Альтернативы:
1. S3-совместимый объектный сервис на своём сервере, если потребуется масштабирование, много экземпляров приложения и независимая эксплуатация (больше компонентов и настроек; не сжимает фото автоматически).
2. Свой каталог и самописный сервис файлов (минимальные зависимости, но нужно заново реализовать приватный доступ, подписанные ссылки, удаление, миграцию и учёт). На первом этапе не рекомендуется.

Текущее извлечение из КП в `app/api/unit-economics/photos/route.ts`: Sharp `resize({width:560,height:560,fit:"inside"})`, WebP `quality:76`; аватары клиент обрабатывает в 256x256 WebP quality 0.82.

**Оптимизация для будущих изображений:** единая обработка при загрузке, с поворотом EXIF, проверкой типов/размеров, запретом увеличения разрешения, ограничением пикселей; для карточек до 1200–1600 px длинной стороны, WebP quality ~80–85 как начальная настройка с визуальным тестом; превью 320–480 px и quality ~70–78, лучше генерировать по запросу/кэшировать; отдельный режим для прозрачности и мелкого текста. AVIF сравнивать по реальным файлам с учётом CPU. Не применять дополнительную потерю качества к уже пережатым изображениям повторно.

Исходные Excel/КП хранить без потери точности/изменения байтов — это документы и источник оригинальных встроенных фотографий. Добавить подсчёт уникальных объектов, возможную дедупликацию по хешу с контролем ссылок и безопасный сбор неиспользуемых изображений. Не удалять оригиналы/файлы до проверки ссылок и резервного восстановления.

Хранение в томе Docker **не является резервной копией**. Нужны зашифрованные копии на отдельный носитель/хост и тест восстановления.

## 3. Прямой доступ к серверу, без VPN и внешних прокси (решение пользователя 19.11.2026)

**Обязательное требование:** сотрудники открывают ПАНДУ с обычных браузеров компьютеров и телефонов по HTTPS, из любых сетей, без VPN, Tailscale, Cloudflare Tunnel и внешних прокси. Не использовать сторонние туннельные сервисы в инфраструктуре.

Поток: браузер -> интернет -> публичный IP офиса -> маршрутизатор/firewall (входящий 443, при необходимости 80 для проверки/перенаправления) -> собственный HTTPS reverse proxy на физическом сервере -> внутренний Docker-сервис ПАНДЫ. Собственный Nginx/Caddy локально не является внешним прокси-провайдером и позволяет завершать TLS перед приложением.

### Адреса

- **Внутренний URL заданий:** `http://panda-web:3000` как пример имени Docker Compose-сервиса; ещё лучше прямые вызовы общей серверной логики, где возможны. Внутренние cron-маршруты обязаны проверять служебную авторизацию. Не открывать их через публичные порты без необходимых защит.
- **Публичный URL:** `https://panda.<собственный домен>` (если куплен/уже есть домен) либо `https://<публичный статический IP>` без домена. Адрес должен реально вести на офисную сеть; нельзя просто придумать адрес, не настроив DNS, маршрутизацию и TLS.
- **Без домена, но с HTTPS:** начиная с 15.01.2026 Let's Encrypt поддерживает публично доверенные IP-сертификаты IPv4/IPv6 сроком около 160 часов (6 дней), поэтому потребуется поддерживаемый ACME-клиент и обязательно отлаженное автоматическое продление/перезагрузка TLS. Проверить совместимость выбранной версии Caddy/Certbot и способ получения/установки сертификата, а не предполагать наличие автоматического IP-TLS по умолчанию.
- **Фактический резерв:** второй URL на тот же физический сервер не обеспечивает отказоустойчивость. Выделенный второй сервер/канал с подготовленным переключением пока в объём первого этапа не входит.

### Обязательные проверки с сисадмином

1. Публичный IPv4/IPv6 адрес с возможностью входящих соединений; отсутствие CGNAT или заказ белого IP/альтернативного прямого канала. Статический IP предпочтителен, особенно без домена.
2. Правила маршрутизатора: проброс и фильтрация TCP 443, при необходимости TCP 80; локальный адрес сервера и политика firewall.
3. Настройка TLS (сертификат на домен или на публичный IP) и автоматическое продление; контроль истечения срока.
4. Публиковать наружу только HTTPS, не открывать напрямую PostgreSQL, Supabase Studio, Redis, админ-порты, внутренние Docker-порты и сервисные эндпоинты без контроля доступа. Учесть, что Docker publishing может обходить привычные правила ufw, использовать корректную политику DOCKER-USER/nftables/маршрутизатора.
5. Противодействие перебору паролей (лимиты попыток/блокировки), HTTPS-only cookies, секреты вне кода, обновления, мониторинг, аудит и резервные копии.
6. Проверка входа с мобильного интернета вне офисного Wi-Fi; проверка работоспособности внешних callbacks только если они используются.

### Отказ от Vercel в коде

- `app/api/wb/daily-sync/route.ts`: убрать `origin="https://zakup-automation.vercel.app"`.
- `app/api/yandex/daily-sync/route.ts`: убрать `VERCEL_PROJECT_PRODUCTION_URL`, `NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL` и fallback `https://zakup-automation.vercel.app`.
- Ошибка отсутствующего внутреннего URL должна быть явной: никакой скрытой отправки запросов на старый Vercel.
- Утверждение о прямом публичном доступе **не означает**, что сервер уже имеет белый IP или настроенную сеть; требуется подтверждение сисадмина.
