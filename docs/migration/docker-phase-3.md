# ПАНДА: этап 3. Изолированная серверная инфраструктура

Дата: 2026-11-19. Ветка: `migration/docker`.

**Статус:** файлы и проверки подготовлены. Никакие рабочие данные, токены, расписания и сервисы не перенесены. Docker Engine на целевом сервере не проверен. Действующая ПАНДА работает как прежде.

## Простая схема

1. Пользователь открывает сайт через обычный браузер по HTTPS. VPN и внешние туннели не используются.
2. **Собственный Nginx на физическом сервере** принимает HTTPS на 443 и отправляет запросы ПАНДЕ (`127.0.0.1:3000`) либо самостоятельному Supabase (`127.0.0.1:8000`) в зависимости от пути.
3. Docker запускает `panda-web`, официальную серверную установку Supabase, включая PostgreSQL 17, Auth и Storage, и отдельный планировщик после разрешённого переключения.
4. Внутренние server-to-server запросы к Supabase идут через частную Docker-сеть `panda_shared`, а подписанные ссылки для фотографий сохраняют публичный HTTPS-адрес.
5. Данные, фотографии и ключи не хранятся внутри одноразового контейнера приложения.

## Добавленные компоненты

| Файл | Функция |
| --- | --- |
| `infra/supabase/prepare.sh` | Получает официальную версию Supabase `self-hosted/v0.8.4` в отдельный каталог; НЕ запускает ничего и не изменяет рабочую базу |
| `infra/supabase/docker-compose.panda.yml` | Дополняет официальный состав, привязывает порты 8000, 5432, 6543 только к 127.0.0.1; подключает частную сеть |
| `compose.server.yaml` | Дополняет контейнер веб-приложения частной сетью, серверным адресом Supabase и отдельными секретными файлами |
| `infra/nginx/panda.conf.example` | Образец собственного HTTPS-приёмника; сертификат для домена или публичного IP необходимо получить и настроить отдельно |
| `infra/docker/entrypoint.mjs` | Читает секреты из отдельных файлов перед запуском приложения |
| `lib/supabase/server-fetch.ts` | Перенаправляет серверный транспорт SDK внутрь сети без выдачи приватных адресов в подписанных ссылках |
| `infra/scheduler/` | Отдельный планировщик с точной копией 20 ежедневных Vercel-заданий и 3 восстанавливающих заданий из PostgreSQL; повторы в одну минуту объединяются, автоматическое включение запрещено |
| `compose.scheduler.yaml` | Планировщик не активен по умолчанию; требуется профиль `cutover` и `SCHEDULER_ENABLED=CUTOVER_CONFIRMED` |
| `infra/supabase/disable-obsolete-cloud-cron.sql` | ОТДЕЛЬНЫЙ ручной скрипт только для восстановленной базы; отключает 3 обращения к Vercel, не трогает задания заметок |
| `.github/workflows/docker-migration.yml` | Проверка конфигурации и полной сборки в изолированном GitHub Actions с тестовыми, нерабочими значениями |

## Правило безопасности

- Docker Compose **2.24.4+** необходим из-за тега `!override`; обычное наложение `ports` добавляет дополнительный порт, поэтому без `!override` официальная Supabase-сборка может случайно опубликовать базу в интернет.
- Публичный доступ только к 443/80 на собственной машине. Непосредственный доступ из интернета к 3000, 8000, 5432, 6543, Studio и внутренним Docker-службам закрыт.
- Хранить `.env.docker`, каталоги `.panda-local/`, `secrets/`, `backups/` вне GitHub и контекста Docker build.
- `PANDA_SECRETS_DIR` указывает на отдельный каталог сервера. Файлы `supabase-secret-key` и `cron-secret` содержат реальные секреты, предоставленные только при запуске. Docker Compose с файловыми secrets может монтировать их с правами исходного файла: **UID 1000** (непривилегированный Node-процесс) должен иметь доступ только к нужным файлам, другие пользователи — нет. Проверить фактические UID/GID и права на целевом Linux. Не делать каталог публичным ради исправления Permission denied.
- `supabase/.env` из официальной поставки содержит **заведомо небезопасные примеры**. Прежде чем запускать стек, выполнить официальные `sh utils/generate-keys.sh` и `sh utils/add-new-auth-keys.sh` из подготовленного каталога, настроить URL и проверить реальные значения.
- Самостоятельные секреты маркетплейсов в зашифрованном Vault; после восстановления исходной БД старые шифротексты Vault могут не расшифроваться с новым корневым ключом, поэтому их нужно безопасно повторно внести через штатную админку, проверив доступ.
- Не выполнять `docker compose down -v` на рабочих данных: эта команда удаляет тома.
- Резервная копия должна включать **БД + файлы Storage + ключ шифрования Vault**, храниться отдельно от сервера и проходить регулярную проверку восстановления.

## Тестовый порядок без отключения работающей системы

1. GitHub Actions проверяет Dockerfile, конфигурацию и запуск страницы входа. Результат сборки должен быть подтверждён отчётом GitHub.
2. На отдельном тестовом сервере или временной изолированной среде установить Docker и проверить полный веб-контейнер.
3. Создать Docker-сеть `panda_shared` и получить официальный Supabase через `bash infra/supabase/prepare.sh /srv/panda/supabase` (команда подготовит файлы, **не** запустит сервисы).
4. Заполнить тестовые ключи, локальные URL, создать секретные файлы, протестировать `docker compose config`. Далее включить официальный Supabase в тесте. Проверить PostgreSQL 17, Auth, Storage, Vault, pg_cron/pg_net.
5. Подготовить резервную копию исходной облачной базы и файлов. Выполнить **пробное** восстановление на отдельном тестовом экземпляре. Важная особенность: Из 4 активных заданий pg_cron **3 действительно ссылаются на старый Vercel**, а задача `app-personal-notes-v1` выполняет SQL локально. Три облачных вызова надо отключить на восстановленной базе в изолированной сети до начала тестового запуска по `infra/supabase/disable-obsolete-cloud-cron.sql`; исходную рабочую БД не менять.
6. Проверить вход 3 пользователей, роли, закуп, финансы, рекламу, Excel, фотографии, 1С и загрузки маркетплейсов. Никакие реальные дневные задания на тестовой установке не запускать без отдельного плана.
7. Закончить аудит всех прямых обращений к публичному URL Supabase: центральные клиенты, критичные ежедневные маршруты и ключевые страницы уже адаптированы; **не все** серверные пути проверены.
8. Согласовать с администратором статический публичный IP, защиту портов, сертификат HTTPS для IP либо домена, права на каталоги, резервные копии.
9. Только при подтверждённом тестовом восстановлении согласовать перенос изменяемых данных, остановку старых cron, сверку истории и безопасное переключение (с возможностью отката).

## Команды проверки, только после получения тестового Linux

```bash
# Версии инструментов
docker version
docker compose version

# Проверить безопасность базы: объединить официальный compose с нашей настройкой
cd /srv/panda/supabase
docker compose config --quiet

# Проверить веб-часть
cd /srv/panda/app
cp .env.docker.example .env.docker
# Заполнить только тестовые значения и проверить права на файлы
docker compose --env-file .env.docker config --quiet
docker compose --env-file .env.docker build panda-web
docker compose --env-file .env.docker up -d panda-web
curl -I http://127.0.0.1:3000/login
```

**Важно:** образец nginx не содержит готового сертификата и не включён в Compose. Не запускать nginx по этому шаблону до согласования реального внешнего адреса и выпуска сертификата. Никаких платных или сторонних прокси не требуется.

## Инженерные ограничения

1. **GitHub Actions не заменяет проверку на целевом сервере.** Сборка при dummy-ключах не доказывает, что миграция базы и роли работают.
2. Восстановление облачного Supabase в самостоятельный отличается от простого переноса каталога PostgreSQL. Использовать официальное руководство по переносу, сохранить Auth/Storage и выполнить пробный restore.
3. В настоящий момент web, scheduler, Supabase и Nginx проектируются как раздельные службы, объединённые внутренней сетью. Подготовка к подключению к реальному IP и TLS завершится только после получения сведений о сервере.
4. PostgreSQL 17 основной системы и PostgreSQL 17 в self-hosted образе могут иметь разные минорные версии; совместимость восстановления проверять на реальных, обезличенных или контролируемо скопированных данных.
